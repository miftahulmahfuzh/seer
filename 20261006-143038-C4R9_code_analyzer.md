## Detailed Requirements Understanding

**Problem statement.** `commands/research_store.py:219` asserts the property *"the `--store`
target is a dev store"* by testing *"the `--store` path equals this process's
`research.STORE_DIR`"*. `STORE_DIR` is derived from `config.REPO_ROOT`, which is
`Path(__file__).resolve().parents[3]` — the location of the **running module**. The two
predicates coincide only when the operator uses the default path inside a single checkout. A
session running in worktree *A* that passes `--store <checkout B>/engine/.research` compares two
genuinely different paths, `_same_dir` returns `False`, and the destructive build proceeds.

**What must change.** The build path needs a second, *content*-based test of the same property:
read the target's `manifest.json`, take the window it declares, and refuse when that window is
the wrong one for this invocation. This is the identical idiom the read-only paths already use
(`_store_window` → `research.declared_window`) and that `lab test` already uses
(`commands/lab.py:484`).

**Success criteria.**

1. `research_store --test-window --store <any checkout>/engine/.research` exits 2 and writes
   nothing, when that directory holds a store whose manifest declares the dev window.
2. `research_store --store <any checkout>/engine/.research-test` exits 2 the same way when that
   directory holds a test store.
3. The existing same-checkout refusals (`:219`, `:227`) still exit 2 with their current messages,
   **including in a worktree where `research.STORE_DIR` does not exist** — see Key Consideration 1.
4. A legitimate first build into a path that does not exist yet still proceeds.
5. The dev store at `engine/.research` still loads at fingerprint `399d0d25…`; `MANIFEST_KEYS`
   stays at 9; `engine/tests/test_research_store.py:236` and `:622` pass unedited.
6. `pytest -q` green in `engine/`; `lab/lab.sqlite` still reads 85 dev trials and 0 test trials.

**Key considerations (the edge cases Q1 names, resolved by measurement).**

1. **A nonexistent target cannot be identified by content, and that case is load-bearing.**
   A fresh worktree does **not** carry `engine/.research` — it is gitignored, so `git worktree
   add` does not materialise it. Measured in the worktree cut for this plan:

   ```
   STORE_DIR      : /home/miftah/.worktrees/seer/research-store-clobber-guard/engine/.research
   exists         : False
   ```

   `engine/tests/test_research_test_store.py:451` asserts
   `cli.main(["research_store", "--test-window", "--store", str(research.STORE_DIR)]) == 2`.
   It passes in that worktree **today, and only because `_same_dir` is pure path comparison** —
   verified by running it there: `1 passed, 27 deselected`. A content-*only* guard returns
   "unknown" for a directory with no manifest and that assertion goes red in exactly the
   environment `/implement` will run in. The content check must therefore be **additive**.

2. **`declared_window` already signals "cannot tell" uniformly.** Measured against four target
   shapes:

   | target | `research.declared_window(d)` |
   |---|---|
   | missing directory | `ValueError: … no research store (manifest.json missing)` |
   | empty directory | `ValueError: … no research store (manifest.json missing)` |
   | unparseable `manifest.json` | `ValueError: … not valid JSON` |
   | manifest with no window keys | `Window(name='dev', …)` |

   One `except ValueError` covers "missing, partial, or unreadable". Treating that as *unknown*
   and falling through is right: a store whose manifest will not parse is already unusable, so
   rebuilding over it destroys nothing, and refusing would block the one workflow that most needs
   to run.

3. **A partial manifest cannot exist in a swapped-in store.** `build_store` writes into
   `<store>.tmp` and `_swap_in` (`research.py:739`) publishes it with `os.replace`. There is no
   window in which `<store>/manifest.json` is half-written.

4. **The lenient default is a feature here.** `_declared_window` (`research.py:969`) returns
   `DEV_WINDOW` whenever `window_end` is absent, whatever else the manifest holds. So a
   partially-keyed dev manifest is still identified as dev, and still refused.

5. **Assumption stated:** a `--store` target that holds a *valid* store of the window being built
   is a legitimate rebuild and is not refused. Only the cross-window case refuses. This preserves
   `research_store --with-fundamentals` and `--refresh-fundamentals` over an existing dev store,
   which the data-pipeline runbook documents as routine.

### Processing chain

1. **Store resolution** — `research_store.py:211-215`
   - Input: `args.store` or, when `None`, `research.TEST_STORE_DIR` if `--test-window` else `research.STORE_DIR`
   - Output: a `Path`, **not resolved, not existence-checked**

2. **Clobber guard, forward direction** — `research_store.py:219` **← the defect**
   - `if test and _same_dir(store, research.STORE_DIR): return 2`
   - `_same_dir` (`:168`) calls `Path.resolve()` on both and compares, falling back to raw `==` on `OSError`
   - `research.STORE_DIR` (`research.py:68`) is `config.REPO_ROOT / "engine" / ".research"`
   - `config.REPO_ROOT` (`config.py:17`) is `Path(__file__).resolve().parents[3]` — **the running module's location**
   - Therefore the comparison is scoped to *this* checkout and silently passes for every other one

3. **Clobber guard, reverse direction** — `research_store.py:227`
   - `if not test and _same_dir(store, research.TEST_STORE_DIR): return 2`
   - Same defect, same cause, lower stake (the test store is rebuildable and is currently absent)

4. **Read-only / refresh branches** — `:234-239` → `_coverage`, `_verify`, `_run_refresh`
   - `_verify` and `_run_refresh` both call `_store_window(store, test)` (`:295`), which calls
     `research.declared_window(store)` and refuses on a window mismatch with exit 2
   - **This is already content-based and already checkout-independent**

5. **Build branch** — `:241-270`
   - `window = research.DEV_WINDOW`, or `research.test_window(...)` under `--test-window`
   - `_build(store, …)` → `research.build_store(…)` → writes `<store>.tmp` → `_seal` → `_swap_in`
   - **No content check anywhere on this path** — the only gate was the name comparison at `:219`

### Data persistence

**Store directory:** `<store>/{bars,dividends,fx,unserved}.csv`, optionally `fundamentals.csv`,
plus `manifest.json`. Written to `<store>.tmp`, published by `_swap_in` (`research.py:739`) via
`os.replace` through a `<store>.old` staging name. Atomic; a failed or killed build leaves the
previous store intact.

**Manifest:** `json.dumps(sort_keys=True, indent=2)`. 9 `MANIFEST_KEYS` always; the 3
`OPTIONAL_MANIFEST_KEYS` (`window_name`/`window_start`/`window_end`) **only when the window is
not dev** (`_seal`, `research.py:731`). Absent means dev — the compatibility hinge that keeps
`engine/.research` loadable at its sealed fingerprint.

### Exit points

Exit 0 ok · 1 build or check failed, or coverage below the floor · 2 store missing/invalid, or a
flag/guard refusal. Side effects: the store directory, and log lines only.

## Answers to the Handover's Three Forks

Recorded here as findings; the decisions they drive are in the plan index's `## Decisions`.

**Q1 — what identifies a dev store?** Both things, in sequence. Content (`declared_window`) is
the predicate that generalises across checkouts, but it is undefined for a target that does not
exist — and that target is not hypothetical: it is `research.STORE_DIR` in every worktree, and an
existing test asserts a refusal there. **Measured, not assumed**: the test passes today only
because of the name check. So the name check stays as the first gate and the content check is
added as a second, with "cannot tell" falling through rather than refusing.

**Q2 — refuse `--store` outside the checkout outright?** **No.** The handover said to check
before assuming; the check finds a live consumer. `.claude/skills/explore-and-experiment-new-method/SKILL.md:31`
instructs Sera's child sessions — which run in their own worktrees — to
`export SEER_RESEARCH_STORE=/home/miftah/seer/engine/.research`, i.e. the main checkout's store
from a different checkout, by absolute path. That is a cross-checkout store reference in daily
use. Separately, `sync-research-store` does **not** rely on `--store`: `sync_store.py:54-67`
resolves the main checkout itself with `git rev-parse --path-format=absolute --git-common-dir`
and copies the directory directly, so it is unaffected either way. A blanket refusal would also
be a *weakening* in a second direction — it would refuse `--verify` against a perfectly good
store in another checkout, which destroys nothing and is a reasonable thing to do.

**Q3 — do the siblings have the gap?** **Only the build path does.**

| path | destructive? | current window check | verdict |
|---|---|---|---|
| build (default and `--test-window`) | **yes** — `_swap_in` replaces the directory | name only (`:219`/`:227`) | **the gap** |
| `--verify` | no — loads | `_store_window` → `declared_window`, content-based | already covered |
| `--refresh-fundamentals` | rewrites `fundamentals.csv` only | `_store_window` → `declared_window`, content-based | already covered |
| `--coverage` | no — loads | `--test-window` refused outright at `:189` | already covered |
| `lab test --store` | no — loads, but spends the one counted look | `declared_window` + `window.name != "test"` (`lab.py:484`), **and** `runner.run_test` again (`runner.py:501`) | already covered, twice |

The siblings reach `declared_window` before touching anything, and `declared_window` reads the
target's own manifest, so they were never checkout-local. They need no code change — they need a
regression test that pins the cross-checkout case, so the coverage is asserted rather than
inferred from reading.
