## 0. In plain words

Seer v0.1.0 is the **paper-only** ship (owner option (b), 2026-10-04). Five strategies trade on
paper every night: SPY buy-and-hold (the champion), A, F4, F1 and C (the news veto). Nothing is
real money. No strategy has passed a backtest gate, so the home screen keeps saying "SPY
buy-and-hold is the champion; Seer recommends no buys".

The code is all on `main`. What is left for v0.1.0 is to prove it runs and then release it:
1. five consecutive nights ran unattended and the replay check is green on Neon;
2. the app shows those nights correctly;
3. the repo gets its README (owner rule: the README is written at release, never earlier);
4. the ROADMAP is marked, and `gh release create v0.1.0` runs.

This is a verify-and-document set, not a feature set. If a check fails, the work is to find and fix
the cause (or stop and report it), not to work around the gate.

## 2. Decisions

### Law: do not reopen

| Topic | Rule |
|---|---|
| Go-live | Design §1, unchanged. v0.1.0 is paper only. Nothing in the README, the release notes or the app may present a real-money buy, a "recommended" strategy or a go-live date |
| The gate is the gate | No release unless the last five scheduled runs are green through Paper and Paper check, and `paper_check --require-sessions 5` exits 0 on Neon. No lowering the count, no `--require-sessions` override, no back-dated sessions, no reset to hide a bad night |
| Frozen roster | No edit to any roster entry, spec, digest, prompt or `FROZEN_MODEL`. A fix that would change a digest is a new id and a new clock. That is out of scope here: stop and report it |
| Honest reporting | The release notes state the paper start date, the sessions counted, the replay result, any `split-affected` row, every failed or retried night, and each strategy's paper return vs SPY so far, including losses. The repo is public on purpose (memory: public by choice); do not soften or omit results |
| Closed records | `docs/backtests/*`, `backtest/registry.py`, `STRATEGY_A*_PARAMS`, `STRATEGY_B_FROZEN` are not edited |
| README timing | The README is written in this set, as the last docs step before the release (owner rule) |
| Read-only UI, Seer v2 design, icon-only buttons | As in the previous handovers. This set changes no UI unless a check finds a bug |

## 4. Scope

**In scope:**
1. **Gate (D1):** the runbook's release checklist items 1–2 on the live system, evidence written to
   the runbook.
2. **App check (D3):** checklist item 3, screenshots in the scratchpad, findings in the runbook
   section from phase 1. A UI bug found here is fixed only if it is a display bug that changes no
   stored data (D2 otherwise).
3. **README.md (D4)** at the repo root.
4. **ROADMAP:** P4 "done <date>: 5 consecutive sessions, replay check passed"; P6 C line updated
   with its paper start; "v0.1.0 release" → "released <date>".
5. **Release (D5–D7):** notes file, merge, CI green, `gh release create v0.1.0`.

**Out of scope:** real money; editing design §1; any roster, spec, digest or prompt change; new
strategies or registry appends; notifications; the trade journal; the "Later (v0.2+)" list;
Vercel or Neon configuration changes; setting secrets.

## 5. Acceptance criteria

1. **Gate evidence.** The runbook's new "Release check — <date>" section quotes: the five scheduled
   run ids with their Paper / Paper check conclusions; the Health check output (`sessions ≥ 5` for
   all five strategies, `paper_status = success`); the full `paper_check --require-sessions 5`
   output with exit code 0. A red gate ends the set here with the reason and the earliest new date.
2. **App check.** Every bullet of checklist item 3 is ticked or reported as a bug, at both widths and
   both themes, against Neon data.
3. **README** exists, satisfies D4, and every link in it resolves to a file in the repo or to
   seertrade.site.
4. **ROADMAP** updated as in §4.4, with dates.
5. **Release** `v0.1.0` exists on GitHub, targets the merge commit on `main`, CI green on it, notes
   satisfy D5. `gh release view v0.1.0` quoted in the termination report.
6. No roster digest moved; `paper_check` is still green after the merge.

## 6. Open questions for the analysis to settle (recommend, don't ask)

- **Rendering against Neon behind Google auth (D3).** Production needs a Google sign-in the session
  cannot do. Find the cheapest honest path, for example a local `next dev`/`next start` with
  `DATABASE_URL` from `.env.local` and a dev-only session, or the demo-free read path phase 6 of the
  C set used. It must not add an auth bypass that ships to production.
- **Paper return numbers for the notes (D5).** Take them from the same code path the Leaderboard
  uses (`web/lib/metrics.ts` / `data.ts`), or from an engine query that gives the same numbers. Say
  which, and check that the two agree on one strategy.
- **Version files (D6).** Does anything already carry a version string? Decide whether to bump.
- **Phase split.** Small and serial is fine: (1) gate check + runbook evidence; (2) app check; (3)
  README + ROADMAP; (4) release notes + release. Phase 1 is the only one that may fail by design.
