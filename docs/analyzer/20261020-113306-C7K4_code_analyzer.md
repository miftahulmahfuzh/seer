## Detailed Requirements Understanding

### Problem statement

`lab.control_draw` is the lab's one matched-draw rule. It builds a blind control arm that holds
the same number of names as the book it controls and takes in the same number of new names each
decision, so the sentence "the book beat a blind draw by N points" is quoted against an opponent
paying the same fees. It shipped on 2026-10-19 and drew thirteen arms (lab trials 841–853). Two
measured defects were recorded and deliberately not fixed:

**Defect 1 — the entry count is estimated from a book that is too fresh.** `matched_names` reads
`real_now` and `real_prev` and uses only `len(real_now)` and `len(set(real_now) - set(real_prev))`.
On a chassis whose real book has a *keep band* — a held name stays while it ranks inside a wider
threshold — `real_prev` cannot be computed without knowing what the book actually held, and no
allocator holds that. Every current caller substitutes a *freshly derived* selection at the
previous decision. On M0208 (hold the top 20 while they rank inside the top 40) a fresh top-20 is
ranked 1–20 and almost nothing falls past rank 40, while the real held set has drifted toward the
edge and falls out far faster. Measured over all 169 of M0208's decisions: **304 estimated entries
against 624 real, 0.487×, uniform across eras** (0.444 / 0.509 / 0.500). Pool attrition forces
extra entries at run time and pulls the realised figure back to 455 trades, which is why the
recorded arm lands at **0.73× trades / 0.76× turnover** rather than at 0.49.

**"624 real entries" is 624 *as the close-out recorded it*, and phase 1's probe is what confirms
it.** `M0208-CGO-N20`'s recorded `trials.trades` is **also 624**, and an entry count and a trade
count are not the same quantity: a book that takes in `e` names and lets `e` go makes about `2e`
basket changes before fills and resizes. If phase 1's forward replay reads near **1248** while the
ratio still lands at ~0.487, the close-out conflated an entry count with a trade count. **The ratio
is the finding and is unaffected either way; the absolute is a cross-check.** Phase 3's own probe
anchors against phase 1's measured number rather than against the literal 624, and **phase 6 owns
the correction of any published sentence that quotes it**.

**Defect 2 — the rule matches names, and turnover is not a property of names.** On a chassis that
weights its names by something other than equal slots, the book engine's 1 %-of-equity resize band
fires on weight drift, not on name changes. `M0221-E50` holds `M0221-C50`'s **exact** fifty names
and records its **exact** 360 trades, and still turns over **0.7126 against 0.4450 — 1.60×**. The
matched draw closes the trade axis on that chassis (371 against 360, 1.03×; a free pre-run probe
read 1.000 basket changes) and leaves the turnover axis at **1.95×**.

### What "done" looks like

- **R1:** a shadow of the real held set is carried across decisions, the thirteen recorded arms are
  byte-for-byte reproducible under their own allocator ids, and every chassis is measured under the
  new rule so that "the shadow changes nothing here" is a recorded measurement and not an
  assumption. Where the shadow moves the entry count, a NEW arm is drawn under a NEW amendment.
- **R2:** the weight-vector mechanism is **measured before it is built**, on a free re-run that
  records no trial. If it brings a weight-varying chassis inside `WARN_BAND` it is written and
  applied; if it does not, that is recorded as a measured dead end and leftover 2 is closed with a
  number rather than carried a third time.
- **R3:** the plan's Why says what the work buys and what it does not.
- **R4:** no `lab test`; `lab run --amend` only; no edit to a recorded candidate, a recorded
  amendment block, or a closed record.

### Key considerations and constraints

1. **A module body is outside `config_digest`.** `registry._canon` renders a candidate by its
   allocator id, its rules id and `dataclasses.fields()` of its params. The *body* of
   `control_draw.matched_names` is in none of them. So an in-place edit to the shared rule would
   move the behaviour of every recorded matched-draw arm **without failing a single test** —
   `test_every_recorded_configuration_still_digests_to_its_recorded_digest` stays green. M0208's
   own file already names this trap in a comment above `_banded_picks`. This is the single most
   dangerous property of the change and it is what the "five recorded arms" constraint is about.
2. **The 473-bar lookback cap is absolute** (`labkit.smoke_market`'s fixture size; every lab
   allocator's `lookback` must fit it). Measured today, allocator by allocator — see the Lookback
   budget table below. It bounds how many extra decisions a backward replay may read.
3. **An allocator cannot read its own weights.** `book_runner` hands the allocator `held`, a
   `frozenset[str]` of symbols, and nothing else about the book. A weight rung cannot be recovered
   from state; it must be derived from something stable, or carried.
4. **Allocator objects are module-level singletons** and `dev.run_registry` reuses one per
   allocator id inside a call, across candidates and across walk-forward folds. Any per-instance
   mutable state leaks between candidates and between folds.
5. **An amendment is cheap and a method id is not.** The luck gate's N counts *methods* since
   2026-10-08, so an amendment under an existing id costs zero N, zero method ids and zero
   test-window looks. The honest-control set proved it: thirteen trials, eight amendments, zero ids.
6. **Old trial returns are not reproducible.** A re-run of a recorded arm does not reproduce its
   recorded columns exactly. Every pre-run comparison must be re-run against re-run inside one
   sweep; only the final `lab control` verdict reads recorded columns against recorded columns.

### Assumptions stated

- `M0225` is still `dev-eligible` with one recorded amendment (`E100`, seq 1), so a seq-2 amendment
  is available to it. Verified read-only against `method_amendments`.
- The direction of remedy 2's effect on turnover is **not known** and is not derivable from the two
  numbers in the brief. See "The weight-vector mechanism, examined" below. The plan therefore puts
  a free measurement in front of it with an explicit STOP.

## Current Dataflow

### Entry point: `book_runner.run_book` → the allocator

**Location:** `engine/src/seer_engine/backtest/book_runner.py:393-403`
**Trigger:** every rank session, and every resize session once a basket exists.
**Input:** `allocator.targets_prepared(prepared, members, data_date, mine, params)` where `mine` is

**Key fact:** `mine` is the **control's** holdings. Nothing in the call carries the *controlled*
arm's holdings, and nothing carries any weight.

### The matched draw, as it stands

```
matched_book(select, data_date, held, tag, seed, cadence)
  ├─ pool_now, real_now = select(data_date)
  ├─ _,        real_prev = select(previous_decision_date(data_date, cadence))
  └─ matched_names(pool=pool_now, held=held, real_now=…, real_prev=…, tag, seed, data_date)
        ├─ size = len(real_now)
        ├─ e    = churn(real_now, real_prev) = |set(real_now) − set(real_prev)|
        └─ matched_partition(pool, held, keep_n = size − e, tag, seed, data_date)
              ├─ keep = (held ∩ pool) sorted by keep_key(tag,seed,s)      [date-free]
              └─ tail = (pool − held) sorted by entry_key(…,month)        [month-keyed]
                      + (dropped holdings) sorted by entry_key(…,month)
```

`real_prev` is the only input the defect lives in. `matched_partition`, `keep_key`, `entry_key`,
`churn` and `previous_decision_date` are all correct and measured.

### The weight axis

| chassis | how the real book weights | how the control weights today |
|---|---|---|
| M0221 / M0225 | `weights()`: the picks' own market values, normalised, 10 % ceiling (`m0221:181-191`) | identical code, applied to the **drawn** names' market values |
| M0047 | `size_weights(sizes, top, p)` over the picks' market values, under a ceiling | identical code, drawn names' sizes |
| M0201 | per-**company** market value, 10 % ceiling, split across held classes | identical code, drawn names |
| M0202, M0208, M0215, M0227, M0243 | equal slots | equal slots |

So the control already weights by **the drawn names' own sizes**. The defect is not that the
control is weighted differently in kind; it is that a blind draw from the sized pool has a much
flatter size distribution than the real top-N, so the ceiling rarely binds and the normalised
weights move differently as prices drift.

## The weight-vector mechanism, examined

This section exists because the plan's phase 4 is a measurement with a real chance of a STOP, and
the reason has to be written down rather than discovered at 2am.

**What the brief's two numbers establish.** `E50` shows that *weighting alone* moves turnover by
0.60 (1.00 → 1.60) on identical names and identical trades. `C50-PLC` is at 1.95. So **at most**
0.60 of `C50-PLC`'s 0.95 of excess is attributable to weighting — about two-thirds, not
three-quarters, and only if the two effects are additive, which nothing has measured.

**What they do not establish: the sign of the remedy.** `M0221-C50` turns over only 0.445 because a
cap-weighted book is nearly *drift-neutral*: the target weight of a name is its market value share,
which moves with its own price, so the realised weight tracks the target and the 1 %-of-equity band
rarely fires. `M0221-C50-PLC` already uses the identical weighting code on its own drawn names, so
it is drift-neutral too — its excess comes from the flatter size distribution (the 10 % ceiling
almost never binds) and from re-normalising over fifty arbitrary names each month.

Attaching **the real book's weight vector** to the drawn names breaks drift-neutrality outright:
the control's target for slot *k* would then move with the *real book's* k-th name's price while
its holding moves with its own. Two uncorrelated drifts cross the resize band more often than one
tracked drift does. **Remedy 2 may therefore raise M0221's turnover rather than lower it**, and the
existing evidence cannot tell us which. A second unknown rides on it: `matched_names` returns its
book in a month-keyed order that re-shuffles every month, so a naive "k-th drawn name takes the
k-th largest weight" would re-assign every rung every month — a turnover generator in itself. The
assignment order is a design choice with its own measurable cost, and the lab has already been
bitten once by exactly this class of thing (an allocator cannot recover its own rung; see
`seer-allocator-cannot-read-its-own-weight`).

**Conclusion carried into the plan.** Remedy 2's direction is unknown, three mutually exclusive
assignment rules are plausible, and all of them can be measured for free through
`dev.run_registry` without recording a trial. Measuring comes first, and a STOP is a legitimate
outcome that closes leftover 2 with a number.

## Can remedy 2 satisfy R1? — the honest read

The original R1 of the honest-control set asked for **one reusable rule**. Three findings bear on
whether remedy 2 can meet it.

1. **Turnover on a weight-varying book is not in name space at all.** `E50` proves it: identical
   names, identical trades, 1.60×. No rule that chooses *which names* a control holds can reach it,
   however the entry count is derived. The matched draw is a name rule by construction.
2. **A weight vector cannot be produced by a shared module.** Each chassis computes its vector with
   its own code — `m0221.weights` (cap, 10 % ceiling), `m0047.size_weights` (size under a ceiling),
   `m0201`'s per-company sizing with class splitting. A shared module has no way to produce any of
   them; only the chassis can. Whatever is shared is therefore the *assignment* of a vector the
   chassis hands over, not the vector.
3. **But that is exactly the shape `matched_partition` already has, and it is already called
   "one rule".** `matched_partition` owns an ordering contract and each of the five chassis that
   use it applies its own slot count, sector cap or keep band to that ordering. By the standard
   already in force in this module, "one shared contract plus a thin per-chassis adapter" *is* one
   reusable rule.

**So the honest answer is two-part, and the plan states it this way.** R1 **as the brief reads it**
— one rule with no per-chassis patch — **cannot be met by remedy 2, and no further work will make
it meetable**, because (1) and (2) are structural facts about where turnover lives, not gaps in the
design. R1 **in the sense `control_draw` already satisfies it** — one shared, tested contract with
a one-call adapter per chassis — is meetable, and that is the most R2 can honestly aim at. These
are two rules on two axes: a **name** rule (`control_draw`) and a **weight** rule. The plan makes
that visible in the file layout rather than hiding it behind one module name (Decision D3).
