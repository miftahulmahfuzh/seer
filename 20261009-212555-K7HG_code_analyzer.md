## Detailed Requirements Understanding

**R1.** `walkforward.evaluate` answers "how did the lab's *selection process* do out of sample": in each fold it picks whichever variant ranked best by MAR on the training slice and scores that. `lab promote` then pre-registers a *different* thing: `store.best_dev_eligible` — the highest-`trials.mar` variant whose derived verdict is eligible, over the whole dev window. The two can disagree, and for M0044 they do: the picks (lighter brakes, ineligible on max-DD) win 3 of 4; `M0044-TV14-N21`, the only eligible variant and therefore the one promoted, wins 1 of 4. The fix adds a second fold condition: the promoted variant's own curve, alone, through the same `evaluate` (single-candidate mapping, so `pick` can only name it), same geometry, same de-funding, same D10 comparability, must be scoreable on every fold and win a strict majority. The existing pick condition stays ("also require").

**R2.** Kin today = `family` string ∪ transitive `parent_id` ancestors (D4). A blend variant is one *candidate* of a method, not a separate method, and its ingredients are other methods' allocators. They **are already recorded machine-readably**: `lab/method.py:config_text` writes `allocator=<ID>` and `registry._canon` renders every allocator nested anywhere in the params as `<ID>`; that text is the digested identity of every trial (`trials.config_text`, append-only). Lab allocator ids are the id of the method that defined them (every `M*` allocator class in `lab/methods/mNNNN_*.py` has `id = "MNNNN"`; `method.py` docstring: "Allocator ids are therefore unique across lab methods"). So no schema change and no new metadata is needed: `ingredients(m)` = every other `M\d{4}` method id named as `<ID>` in any of `m`'s dev trials' `config_text`. New kin = old kin ∪ ⋃ over ingredients i of ({i} ∪ family(i) ∪ ancestors(i)).

## Current Dataflow

### Entry Point: `lab promote <M>`
**Location:** `commands/lab.py:1298 _promote` → `hardgate.check(conn, M)` → `prereg.promote_method`.

### Processing Chain
1. `hardgate.check` (`hardgate.py:626`): status ≠ dev-eligible → return. `geometry(conn)` cuts 4 folds from `REF-SPY-HOLD`. `fold_record` → `_dev_curves` (all dev trials with curves) → `mismatches` (D10) → `trial_deposits` per trial → `wf.evaluate(curves, bench, folds, deposits)` → `Record`. Refuses if scored < folds, < MIN_FOLDS, or not `majority`. Then `failed_kin` → refuses on any.
2. `wf.evaluate`: per fold, `pick` = argmax training-slice MAR over *all* variants; score that variant's eval slice vs bench's.
3. `prereg.promote_method`: `store.best_dev_eligible` (max `trials.mar` among verdict-eligible dev trials) is the pre-registered candidate; records `fold_text` and `family_text`.
4. `failed_kin` (`hardgate.py:557`): ancestors via `parent_id` (cycle-safe) ∪ same `family`, minus self; `SELECT … status='test-failed'`.

### Other consumers
- `lab status` → `_hard_gate_states` → `summary` + `check` per dev-eligible method → "Promotable now" / "Refused by the hard gate".
- `lab walkforward` → `hardgate.failed_kin` → `wf.buy_signal(…, family_failed=…)`.
- `prereg.family_text` / `lab test`'s kin note → `failed_kin`.

### Data Persistence
None: the gate is read-only SQL + arithmetic; a refusal leaves DB and repo byte-identical.
