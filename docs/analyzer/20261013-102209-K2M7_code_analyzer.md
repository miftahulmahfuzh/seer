## Detailed Requirements Understanding

**Problem statement.** `hardgate.failed_kin` answers "is this method kin to a method that already
failed the test window?" It is the lab's defence against spending a scarce, spend-once test look
re-running a bet that already lost. Today it answers at **method** granularity, and the committed
lab has reached a state where it refuses every method it holds: 0 of 81 are promotable.

**What is actually wrong.** A test look is spent on **one variant** — `promote_method`
pre-registers the single candidate `promoted_variant` returns. The gate refuses the whole method
when **any** of its dev variants is a behavioural twin of a failed book. For several methods, the
variant that would actually be pre-registered is not a twin at all; the twins are siblings that
will never be tested.

**What the original design said about exactly this**, and why it must be engaged rather than
bypassed — `hardgate.py:292-299`:

> Why every dev variant and not only the promoted one. The cost is identical today. Every variant
> is a candidate in every fold's pick, which is (D10)'s reason for refusing on any one variant; and
> kin is a statement about a *method* [...] The price is stated rather than hidden.

Three reasons, and they do not age alike:

1. **"The cost is identical today."** This premise has **expired**. It is now false — measured
   below, the two granularities give different answers for six methods.
2. **"Every variant is a candidate in every fold's pick."** This remains **true and load-bearing**,
   and it is the reason the naive version of this change is unsafe. See the fold-pick measurement.
3. **"Kin is a statement about a method, which has no single variant."** True of `family_state`
   and the buy signal, but a method whose `promoted_variant` is `None` has no variant to speak of
   — so the new rule needs a defined answer there, and that answer must be to block.

**Success criteria.** The gate refuses a method when the book that would actually be tested is, or
rests on, a twin of a failed book — and otherwise allows it. All four callers continue to read one
definition. No recorded row, digest or prereg file changes. The test window is not read.

**Key consideration — the leak the naive change opens.** `fold_record` scores, per fold, the
variant the lab's own rule would have picked knowing nothing past the train end. Those picks are
drawn from **every** variant. A method can therefore have a clean promoted variant while the fold
record that makes it *eligible* was won by its twin siblings. Gating only on the promoted variant
would admit such a method on a record it did not earn — laundering a failed book's performance into
a fresh test look, which is the precise failure the gate exists to prevent.

**Assumption stated.** `promoted_variant` is the single authority on "the variant that would be
pre-registered". Where it returns `None` or raises, the method is not promotable for an unrelated
reason and the kin answer must fail closed.

## Current Dataflow

### Entry Point: `hardgate.failed_kin(conn, method_id)`

**Location:** `engine/src/seer_engine/lab/hardgate.py:1142`
**Trigger:** called by four sites (below)
**Returns:** `tuple[str, ...]` — every method in the kin set reading `test-failed`; `()` when clean
**Raises:** `store.LabError` when the behavioural comparison cannot be made honestly — no
benchmark, or a curve on other or unknown prices (D10) — rather than reading "clean"

**The three arms it unions:**

1. **Lineage** — `_lineage(conn, row)` at `:914`: `methods.family` union the transitive
   `parent_id` walk (cycle-guarded). (D4)
2. **Ingredients** — `ingredients(conn, method_id)` at `:934`: every other lab method whose
   allocator id appears in one of this method's dev `trials.config_text`, plus that ingredient's
   own lineage. One hop. (D12)
3. **Behavioural** — `behavioural_kin(conn, method_id)` at `:1080`: for every test-failed method,
   its **tested** variant's dev curve compared against **every** dev variant of this method —
   monthly returns, de-funded, less each series' own fit on the benchmark's, correlated over shared
   months. The best pair at or above `KIN_CORRELATION` is a `Twin`. (D14)

### Processing Chain

1. **`_lineage()`** — `:914` → set of method ids (includes self; discarded by caller)
2. **`ingredients()`** — `:934` → reads `trials.config_text` via `_INGREDIENT` regex, keeps only ids present in `methods`
3. **`behavioural_kin()`** — `:1080` → `tuple[Twin, ...]`; `Twin` at `:962` carries `failed_id`, `candidate_id`, `failed_candidate_id`, `correlation`
4. **`failed_kin()`** — `:1142` → unions arms 1+2, filters to `status='test-failed'`, then unions arm 3's `failed_id`s

### Exit Points — the four callers that must never disagree

| Caller | Location | What it does with the answer |
|---|---|---|
| `hardgate.check` | `hardgate.py:1527` | raises `store.LabError` → `lab promote` refuses |
| `family_state` | `hardgate.py:1187` (`failed_kin` at `:1194`) | `"clean"` / `"blocked: … read test-failed"`, written by `prereg` into `docs/lab/prereg/MNNNN.md` |
| `runner` (`lab test` note) | `runner.py:907` | records what was true the day the look ran; does **not** re-gate (D3) |
| `lab walkforward` buy signal | `commands/lab.py:2429` | passed to `walkforward.buy_signal` as `family_failed` |

`(D9)` and `(D13)` state the invariant explicitly at `hardgate.py:309-311`: *"`failed_kin` stays the
one definition of kin"*, because *"two commands giving opposite answers about one method is worse
than either answer."*

### State Changes

**None.** `failed_kin` and everything it calls are read-only over `lab/lab.sqlite`. No research
store is opened, no backtest runs, no row is written.
