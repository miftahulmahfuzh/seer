## Detailed Requirements Understanding

**Problem Statement.** On 2026-10-07 the owner revised design §1 item 1 from
"≥ 3 months of forward paper **and** ≥ 100 closed trades" to "≥ 18 months of forward paper"
(commit `ba8a05b`, design §13). Go-live condition #1 stopped being two clauses and became one,
so the number of rules the web checks fell from six to five.

The revision was applied to the two modules that *compute* the rules (`web/lib/metrics.ts`,
`web/lib/golive.ts`, and their engine twins). It was not applied to the two places that
independently *spell* the same rules for display. Both now state the pre-revision rule:

1. `web/app/(app)/leaderboard/view.ts` still counts six, so the Leaderboard renders
   five rows under `x/6` and `ready` is unreachable.
2. `web/app/sera/how/view.ts` still spells "3 months and 100 trades" in the pipeline diagram's
   paper stage.

**Success Criteria.**

- The Leaderboard's score denominator equals the number of rows it renders, for every roster
  strategy and for a strategy with no gate.
- A strategy that passes all five rules reads `5/5` and "All five pass. / Ready for real money".
- `/sera/how` states the paper bar as design §1 states it today.
- The count has exactly **one** definition in the web, beside the list it counts, and a test
  fails if the list and the count disagree. This is the part that stops the bug recurring; the
  rest is arithmetic.
- No engine file, no migration, no database read, no rendered number other than the ones above.

**Key Considerations.**

- **`scoreOf`'s length guard is load-bearing and must stay.** `page.tsx` passes `items = []` when
  a strategy has no gate row, and the readme pins that case as a `0/6` "Paper only" line. If the
  denominator became `items.length` that case would read `0/0`. The guard is what keeps a missing
  checklist from reading as a passing one.
- **The engine's `checklist` has four items, not five, and is correct.** The fifth rule (the
  backtest gate) comes from `strategies.params.backtest_gate`, a roster fact no backtest can
  evaluate, so the web adds `gateItem` and the engine does not. The engine/web parity test
  compares labels, not lengths, so nothing in the engine needs to move. **Invariant: no file
  under `engine/` is touched.**
- **The lab's six hurdles are a different six and must not be touched.** `lib/sera/derive.ts`'s
  `CONDITION_KEYS` (spy, drawdown, pf, trades, owner, dsr) is the *dev gate*, which still has
  `>= 100 trades` — `data/lab.json`'s `gate.minTrades` is 100 today. `web/app/sera/how/view.test.ts:116`
  pins that list and is correct. The collision of the word "six" across two unrelated gates is
  the main way this fix could go wrong.
- **The existing test actively encodes the bug.** `view.test.ts:294` reads
  *"is never ready with fewer than six items"* and asserts that five passing items are not ready
  — which is exactly the production input. Flipping `CHECKS` without rewriting that test turns a
  green suite red, and the test, not the code, is what was wrong.

## Root cause

`ba8a05b` *"feat(golive): item 1 is 18 months of forward paper, and counts no trades"*,
2026-10-07, touched 21 files. Its web half was exactly four:

```
web/lib/golive.ts          web/lib/golive.test.ts
web/lib/metrics.ts         web/lib/metrics.test.ts
```

It did not touch `web/app/(app)/leaderboard/view.ts`, `view.test.ts`, or
`web/app/sera/how/view.ts`. The engine half of the same commit shows the pattern it *did* guard
against — `gate_checks()` was introduced in `backtest/metrics.py` precisely because four call
sites wrote `checklist(...)[2:5]` and a shortened list silently made every slice wrong:

> **Why this exists rather than a slice.** […] When design §13 dropped the trades item on
> 2026-10-07 the list shortened, every one of those slices silently became the wrong three items,
> and 96 tests failed at once. Selecting by meaning rather than by position means the next change
> to `checklist` cannot do that again.

Ninety-six Python tests failed loudly and were fixed. The TypeScript side had no equivalent
coupling to fail: `view.ts` holds a *literal* 6 rather than a reference to the list, and
`view.test.ts` feeds `scoreOf` hand-built six-element arrays rather than `checklist()`'s output.
Nothing connected the number to the thing it counts, so nothing broke when the thing changed.

**This is therefore a test-shape bug before it is a constant bug.** Setting `CHECKS = 5` fixes
today's symptom and leaves the identical trap armed for the next revision of §1.
